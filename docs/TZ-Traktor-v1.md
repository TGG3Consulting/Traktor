# ЧАСТЬ 1. ОСНОВА

## 1.1 Цель продукта
Соединить владельцев техники (исполнителей) и заказчиков работ. Заказчик публикует задание с параметрами и ценой; исполнители откликаются или торгуются в обратном аукционе; сделка, исполнение, оценка и вся история остаются внутри платформы. Каждой стороне даём встроенный мини-CRM с аналитикой.

## 1.2 Термины
| Термин | Значение |
|---|---|
| Заказчик (Client) | Пользователь, публикующий задания |
| Исполнитель (Owner) | Владелец техники, выполняющий задания |
| Задание (Job) | Опубликованная работа с параметрами и ценой |
| Отклик (Offer) | Согласие исполнителя на цену или контр-предложение (режим фикс-цены) |
| Ставка (Bid) | Предложение цены в обратном аукционе |
| Сделка (Deal) | Подтверждённая пара «задание + исполнитель» с зафиксированной ценой |
| Единица техники (Unit) | Конкретная машина в парке исполнителя |
| Скоринг | Автоматическая оценка ставки: цена + рейтинг + соответствие |

## 1.3 Роли и права
1. **Гость** — просмотр публичной ленты заданий и профилей (только Web, для SEO и виральности); любое действие → экран регистрации.
2. **Заказчик** — CRUD своих заданий, выбор исполнителей, чат по сделке, оценка, CRM-раздел «Мои расходы».
3. **Исполнитель** — CRUD своей техники, отклики/ставки, ведение сделки, CRM-раздел «Мой бизнес».
4. **Двойная роль** — один аккаунт может быть обеими ролями; переключатель в профиле; интерфейс перестраивается (см. 2.4). По умолчанию новый пользователь выбирает стартовую роль при онбординге.
5. **Оператор техники** (v2, заложить в модель данных) — сотрудник исполнителя с ограниченными правами (видит назначенные сделки, отмечает статусы, без доступа к деньгам).
6. **Админ / Модератор** — веб-панель: верификация, споры, каталог, контент, метрики.

## 1.4 Языки и регион
- Локализации с первого релиза: **армянский (hy), русский (ru), английский (en)**. Язык выбирается на онбординге, меняется в настройках, по умолчанию — язык системы.
- Валюта v1: **AMD (драм)**, формат `100 000 ֏`. Архитектурно — поле `currency` в каждой денежной сумме (ISO 4217), чтобы добавить рынки позже.
- Часовой пояс: Asia/Yerevan по умолчанию; все таймстампы храним в UTC, показываем в локальном.
- Телефоны: маска +374 XX XXXXXX по умолчанию, но поддержка любого E.164.

## 1.5 Технологический стек (v1.2 — ПЕРЕСМОТРЕН, действующая редакция в ЧАСТИ 6 и docs/arhitektura-v1.md)
- **Клиенты: Flutter 3.x** (stable), Dart 3. Одна кодовая база: iOS 14+, Android 8+ (API 26+), Web + отдельное Flutter-Web-приложение админки. Riverpod 2 + go_router — без изменений.
- **Бэкенд (изменено 13.08.2026):** мультисервисная архитектура — 9 доменных сервисов на **Go**, GCP Cloud Run, **PostgreSQL 16 + PostGIS** (источник истины), Pub/Sub + transactional outbox, Redis, **Centrifugo** (realtime WS), Cloudflare Edge + **R2** (медиа), Typesense (поиск). Полные решения и обоснования — 15 ADR в docs/arhitektura-v1.md.
- **Firebase остаётся только как:** FCM (push), Crashlytics, Analytics, Remote Config. Firestore/Firebase Auth/Cloud Functions из ядра ИСКЛЮЧЕНЫ (обоснование: ADR-4, ADR-6).
- **Карты (изменено):** MapLibre GL + тайлы OSM/Protomaps; геокодинг Photon + платный fallback (ADR-12). Google Maps SDK исключён из-за стоимости на масштабе.
- **Платежи:** v1 — вне приложения (фиксация суммы), v2 — Idram / Telcell через billing-сервис с ledger двойной записи; Transaction в модели с первого дня.
- Изображения: сжатие на клиенте до ≤1600px, WebP q80; presigned-загрузка в R2, обработка (thumbnails, blur-hash, EXIF-strip, pHash-дедуп) — media-сервисом.

# ЧАСТЬ 1Б. ДИЗАЙН-СИСТЕМА И UX-ФУНДАМЕНТ
*(основано на актуальных best practices мобильного и веб-UX 2026: bottom-nav ≤5 табов, FAB для главного действия, trust-элементы маркетплейсов, скорость как фактор конверсии)*

## 1.6 Принципы
1. **Mobile-first, thumb-first.** Все ключевые действия — в нижней трети экрана. Минимальная зона касания **48×48 dp**, между соседними целями ≥8 dp.
2. **3 секунды до сути.** Пользователь без обучения должен понять: «здесь заказывают технику / здесь находят работу». Никаких каруселей-туториалов из 5 экранов — вместо этого progressive onboarding: подсказки появляются в момент первого использования функции.
3. **Скорость = конверсия.** Скелетоны (skeleton screens) вместо спиннеров на всех списках; кэш последней ленты — мгновенный показ при повторном входе; optimistic UI на ставках и лайках.
4. **Доверие на каждом экране.** Бейдж «Проверен ✓», рейтинг со счётчиком («4,8 · 36 работ»), счётчики активности («12 откликов за час»), фото техники обязательны.
5. **Одно главное действие на экран.** Primary-кнопка всегда одна, закреплена снизу (sticky bottom CTA), не скроллится с контентом.
6. **Ошибки — человеческим языком** + всегда предлагаем следующее действие («Повторить», «Изменить», «Написать в поддержку»).
7. **Доступность:** контраст текста ≥4,5:1; поддержка Dynamic Type / масштабирования шрифта до 130% без ломки макета; все интерактивные элементы имеют semanticLabel (screen readers); не передаём смысл только цветом (к цвету — иконка/текст).

## 1.7 Цвет и тон
> Реализация токенов — в БРЕНДБУКЕ `design/brand/` (tokens.css, tokens.dart); логотип — концепт B «T-балка». Значения ниже — исходные из ТЗ; действующий источник для кода — файлы токенов брендбука. Весь визуал только оттуда.
- **Primary:** глубокий оранжево-янтарный `#E8730C` (техника, каски, «стройка») — CTA, активные состояния.
- **Dark base:** `#1A1D21` (графит) — текст, tab bar в тёмной теме.
- **Поверхности:** светлая тема `#FFFFFF`/`#F5F6F8`; тёмная тема `#1A1D21`/`#23272C`. **Обе темы обязательны** с v1, переключение: системная/светлая/тёмная.
- **Семантика:** успех `#2E9E5B`, предупреждение `#E5A400`, ошибка `#D64545`, информация `#3478C6`.
- **Аукцион:** таймер обычный — нейтральный; < 1 часа — янтарный; < 5 минут — красный + лёгкая пульсация.
- Тон интерфейса: деловой, короткий, без канцелярита. Обращение на «вы». Микротексты локализуются отдельным файлом (ARB).

## 1.8 Типографика и сетка
- Шрифт: **Inter** (кириллица + латиница) / системный фолбэк; армянский — Noto Sans Armenian.
- Шкала: H1 24/32 semibold, H2 20/28 semibold, H3 17/24 semibold, Body 15/22 regular, Caption 13/18 regular, Price 20/28 bold tabular-nums (цены — всегда табличные цифры, чтобы не «прыгали» в аукционе).
- Сетка: базовый шаг **4 dp**; отступы контента 16 dp (моб), 24 dp (планшет/web); радиус карточек 12 dp, кнопок 10 dp.
- Breakpoints (web/планшет): `<600` — телефонный макет; `600–1024` — 2 колонки, навигация остаётся снизу→сбоку (NavigationRail); `>1024` — desktop: левый сайдбар, контент до 1200 px, карта+список рядом.

## 1.9 Навигация
**Мобильная (bottom bar, 5 табов, у каждой роли свой набор):**

| Таб | Заказчик | Исполнитель |
|---|---|---|
| 1 | Главная (мои задания + статусы) | Лента заданий (поиск работы) |
| 2 | Поиск исполнителей/техники | Мои ставки и отклики |
| 3 | **[+] Создать задание** (FAB по центру) | **[+] Быстрый отклик / добавить технику** (FAB) |
| 4 | Сообщения (чаты + уведомления) | Сообщения |
| 5 | Профиль + CRM «Расходы» | Профиль + CRM «Мой бизнес» |

- Центральная кнопка — приподнятый FAB в вырезе таб-бара, цвет primary.
- Бейджи непрочитанного: на «Сообщения» (число), на «Мои ставки» — точка при событии «вашу ставку перебили».
- **Web >1024:** левый сайдбар с теми же 5 пунктами + логотип + переключатель роли; правый верхний угол — колокольчик уведомлений, аватар, переключатель языка.
- Deep links: `traktor.app/job/{id}`, `/auction/{id}`, `/profile/{id}` — открываются и в web, и в приложении (universal links / app links).

## 1.10 Общие компоненты (единый UI-kit, файл design_system/)
Кнопки (primary/secondary/ghost/destructive; states: default/pressed/loading/disabled), поля ввода (лейбл сверху, helper/error снизу, счётчик символов), чипы-фильтры, карточка задания, карточка техники, карточка ставки, bottom sheet (все второстепенные сценарии — в шитах, не в новых экранах), диалог подтверждения (для необратимых действий — с явным описанием последствий), toast/snackbar (3 сек, с Undo где возможно), skeleton-плейсхолдеры, empty state (иллюстрация + 1 фраза + 1 кнопка), рейтинг-звёзды, таймер аукциона, степпер визарда, badge статуса.

**Статусы — единая цветовая карта** (используется везде: карточки, деталки, CRM):
`Черновик` серый · `Опубликовано` синий · `Идёт торг` янтарный · `Выбор исполнителя` фиолетовый · `Подтверждено` бирюзовый · `В работе` оранжевый · `Ожидает приёмки` голубой · `Завершено` зелёный · `Спор` красный · `Отменено` тёмно-серый.

## 1.11 Состояния экранов (обязательны для каждого экрана)
Каждый экран сдаётся в 5 состояниях: **loading** (skeleton), **content**, **empty** (иллюстрация + CTA: напр. «Заданий поблизости нет — расширьте радиус»), **error** (текст причины + Повторить), **offline** (баннер «Нет соединения», кэшированные данные с пометкой времени). Формы — состояние **saving** с блокировкой повторного сабмита.

# ЧАСТЬ 2. ЭКРАННАЯ СПЕЦИФИКАЦИЯ

## 2.1 Splash и онбординг
- **Splash** ≤2 сек: логотип, проверка сессии. Есть сессия → сразу домашний экран роли (никаких промежуточных экранов).
- **Онбординг (первый запуск):** 1 экран выбора языка (hy/ru/en, флаги не используем — названия языков на самих языках) → 1 экран ценности с двумя большими карточками-ролями: «🔧 У меня есть техника — хочу зарабатывать» / «📋 Мне нужна техника — есть задание». Выбор роли = переход к регистрации. Внизу ссылка «Просто посмотреть» (гостевая лента, web-паритет).
- Роль можно сменить/добавить позже — выбор не пугающий, подпись «это можно изменить в любой момент».

## 2.2 Регистрация / вход (Auth)
1. Экран телефона: поле с маской +374, автофокус, цифровая клавиатура. Чекбокс согласия с офертой и политикой (ссылки). Кнопка «Получить код» активна только при валидном номере и чекбоксе.
2. Экран OTP: 6 ячеек, автоподстановка SMS-кода (iOS/Android), автопереход при вводе 6-й цифры. Таймер повторной отправки 60 сек («Отправить снова через 0:59»), после — кнопка. 3 неверных кода → пауза 5 мин с понятным текстом. Ссылка «Изменить номер».
3. Первый вход: имя (обязательно, 2–50 симв.), фото (опционально, подсказка «с фото доверяют в 3 раза чаще»), город/регион (автоопределение по гео с разрешением, можно вручную).
4. Ошибки сети/лимитов SMS — человеческим языком + «Повторить».
- Web: тот же флоу; дополнительно заложить (фиче-флагом) вход по коду из Telegram-бота на случай проблем с SMS-доставкой.

## 2.3 Профиль пользователя (свой)
- Шапка: аватар, имя, телефон (скрыт для других до сделки), рейтинг + число работ, бейдж «Проверен ✓», дата регистрации («На Traktor с марта 2026»).
- Секции: Мои данные · Моя техника (для исполнителя) · Переключатель роли · Язык · Тема · Уведомления (тонкая настройка по типам событий) · Поддержка (чат) · Оферта/политика · Выйти · Удалить аккаунт (двойное подтверждение, 30-дневный grace period).
- **Чужой профиль:** имя, фото, рейтинг, отзывы (список с пагинацией), парк техники (для исполнителя), число выполненных работ по категориям, «На платформе с …». Без телефона. Кнопка «Пожаловаться».

## 2.4 Переключатель роли
- В профиле и в сайдбаре (web): сегмент-контрол «Я заказчик / Я исполнитель». Переключение мгновенно перестраивает таб-бар (см. 1.9) с лёгкой анимацией. Состояние хранится в User.activeRole, синхронизируется между устройствами.

## 2.5 Техника исполнителя
**Список «Моя техника»:** карточки (фото, название, категория, статус верификации цветным бейджем, счётчик «выиграно работ»). FAB «Добавить технику». Empty state: «Добавьте первую машину — без техники нельзя делать ставки».
**Визард добавления (4 шага, прогресс-бар сверху, черновик автосохраняется):**
1. Категория: дерево из каталога (Земляные работы → Экскаватор → Гусеничный/Колёсный…), поиск по названию.
2. Данные: марка (автоподсказки популярных: JCB, CAT, Komatsu, МТЗ, КамАЗ…), модель, год (1980–тек.), характеристики — **динамические поля из specTemplate категории** (для экскаватора: объём ковша м³, глубина копания м; для самосвала: грузоподъёмность т, объём кузова м³; для крана: стрела м, грузоподъёмность т).
3. Фото: 1–8 шт., первое = обложка, drag-переупорядочивание; подсказка «снимите технику сбоку при дневном свете»; проверка на дубликаты по хэшу.
4. Документы (для бейджа «Проверен ✓»): фото техпаспорта/свидетельства. Можно пропустить → техника публикуется как «Без проверки» (участвует в откликах, но ниже в скоринге; плашка-мотиватор «Проверенные получают в 2 раза больше заказов»).
- Сабмит → статус `pending` → админ проверяет ≤24 ч → push «Техника одобрена ✅ / отклонена (причина)».

## 2.6 Создание задания (визард заказчика, 5 шагов)
Автосохранение черновика после каждого шага (возврат в любой момент, черновики видны на Главной). Прогресс: «Шаг 2 из 5».
1. **Что нужно сделать:** категория работы (крупные плитки с иконками: Копка/земляные · Перевозка · Кран/подъём · Снос · Сельхоз · Расчистка/снег · Другое) → подкатегория техники ИЛИ переключатель «Опишу задачу — пусть исполнители сами предложат технику».
2. **Параметры:** название (авто-генерируется из категории+объёма, редактируемое, ≤80 симв.), описание (≥20 симв., подсказки-шаблоны по категории: «длина траншеи, глубина, тип грунта, есть ли подъезд»), числовые параметры из specTemplate (объём/метры/тонны/часы — выбор единицы), фото места (0–6, сильно повышает отклики — показываем это подсказкой).
3. **Где и когда:** карта с пином (drag), поле адреса с автодополнением, уточнение «подъезд для техники есть/нет/не знаю»; даты: «как можно скорее» / диапазон дат / конкретная дата+время начала.
4. **Цена и режим:** сумма (клавиатура с разрядами, подсказка медианных цен по категории, когда накопится статистика — «похожие задания: 80–120 тыс ֏»); переключатель режима:
   - «Фиксированная цена» — исполнители принимают или предлагают свою;
   - «Обратный аукцион» — раскрываются поля: длительность (6ч / 12ч / 24ч / 48ч / своя, макс 7 дней), опция «минимальная цена, ниже не считать» (reserve, скрыта от исполнителей), автопродление при ставке в последние 5 мин (вкл по умолч.), окно моего решения после финиша (12ч по умолч.). Инфо-блок «Как работает аукцион» (bottom sheet с 3 пунктами).
5. **Проверка и публикация:** превью карточки «как увидят исполнители», кнопка «Опубликовать». После публикации — success-экран: «Задание опубликовано! Обычно первые отклики приходят в течение часа» + кнопка «Поделиться» (ссылка traktor.app/job/id — важна для сарафана).
- Валидации на каждом шаге, кнопка «Далее» неактивна с подсказкой чего не хватает. Модерация пост-фактум: автофильтр запрещённых слов, жалобы.

## 2.7 Лента заданий (главный экран исполнителя)
- Сверху: поисковая строка + горизонтальные чипы-фильтры (Мои категории ✓ по умолчанию · Радиус: 10/25/50/100 км/вся страна · Режим: все/аукцион/фикс · Сортировка: новые/ближе/дороже/скоро финиш аукциона).
- Переключатель **Список / Карта** (иконка справа). Карта: кластеры пинов, тап по пину → мини-карточка снизу.
- **Карточка задания:** категория-иконка, название, цена крупно (для аукциона — текущая лучшая ставка + зачёркнутая стартовая), расстояние, город, «нужна к: дате», бейдж режима («⚡ Аукцион · осталось 3ч 12м» с живым таймером в карточке), счётчики (5 откликов · 47 просмотров), фото-превью если есть.
- Pull-to-refresh; бесконечная подгрузка по 20; новые задания при открытой ленте — плашка сверху «3 новых задания ↑».
- **Подписка на фильтр:** кнопка «🔔 Уведомлять о таких заданиях» — создаёт сохранённый фильтр, push при появлении совпадения (ядро retention исполнителя).

## 2.8 Деталка задания (исполнитель)
- Галерея фото → название, статус, цена/лучшая ставка, параметры таблицей, описание, карта-миниатюра (примерная зона ~500 м до сделки, точный адрес — после подтверждения), профиль заказчика (имя, рейтинг, число заказов), счётчики активности.
- **Sticky CTA снизу, по режиму:**
  - Фикс: две кнопки — «Принять цену 100 000 ֏» (primary) / «Предложить свою» (secondary → bottom sheet: цена, комментарий ≤200, выбор своей единицы техники, срок «когда смогу»).
  - Аукцион: блок торга (см. 2.9).
- Если у исполнителя нет одобренной техники подходящей категории — CTA заменена на «Добавьте технику этой категории, чтобы откликнуться» → визард 2.5.
- Кнопки: Поделиться, В избранное, Пожаловаться.

## 2.9 Экран обратного аукциона (ключевой экран продукта)
**Верхний блок (закреплён):** большой таймер `03:12:45` (часы:мин:сек, живой; цветовая логика из 1.7), текущая лучшая ставка крупно, стартовая цена зачёркнута, число участников.
**Лента ставок (реалтайм, без обновления руками):** анонимизированные строки «Исполнитель №3 · ★4,8 · 12 работ — 87 000 ֏ · 2 мин назад», лучшая подсвечена. Имена скрыты до конца аукциона (защита от сговора и переманивания), рейтинг виден (доверие).
**Моя ставка (панель снизу):** поле суммы + степперы −1000/−5000; live-валидации: «ставка должна быть ниже текущей лучшей» (если включён шаг — минимум на шаг), «нельзя ниже 30% от стартовой» (антидемпинг-предохранитель); выбор единицы техники; кнопка «Сделать ставку 85 000 ֏» → **диалог-оферта:** «Ставка — это обязательство выполнить работу за эту цену. Отозвать можно не позднее чем за 2 часа до финиша». Optimistic UI: ставка появляется мгновенно, при конфликте (кто-то успел ниже) — корректный откат с тостом.
**События:** мою ставку перебили → push + строка в ленте подсвечивается; последние 5 минут → баннер «Финальный отсчёт»; ставка в последние 5 мин → таймер продлевается +10 мин с анимацией и системным сообщением в ленте «Аукцион продлён».
**Финиш (Cloud Function по таймеру):** расчёт скоринга всех активных ставок: `score = 0.6·нормализованная цена + 0.25·рейтинг + 0.15·(расстояние + соответствие техники)`; ставки ниже reserve не участвуют. Победитель → статус «предварительно выбран», всем участникам — результат.
**Экран результата для заказчика (окно решения, таймер 12ч):** топ-ставки списком с полными профилями (имена уже раскрыты), победитель по скорингу помечен «Рекомендуем»; три действия: «Подтвердить» (primary) · «Выбрать другого» (тап по любой ставке) · «Отказаться от всех» (confirm-диалог «Задание будет закрыто. Исполнители получат уведомление», без штрафа). Молчание всё окно → авто-закрытие, всем участникам вежливое уведомление.
**Для исполнителя:** «Вы победили — ждём решения заказчика (до 14:00 завтра)» / «Заказчик подтвердил 🎉» / «Аукцион завершён, выбран другой исполнитель» (с кнопкой «Похожие задания»).

## 2.10 Отклики по фикс-цене (заказчик)
- Экран «Отклики (7)»: карточки — исполнитель (фото, имя, ★, работ), его техника (фото, модель), цена (моя/контр-оффер выделен), комментарий, «когда сможет». Сортировка: по скорингу (деф.) / цене / рейтингу.
- Действия по карточке: «Выбрать» → confirm → сделка; «Задать вопрос» (пред-сделочный чат, телефоны маскированы, автофильтр обмена контактами в тексте — мягкое предупреждение); «Отклонить» (с необязательной причиной — исполнителю уходит корректное уведомление).
- Контр-оффер: заказчик может принять его или ответить своей ценой (1 раунд повторного торга, чтобы не превращать в базар).

## 2.11 Сделка (общий экран для обеих сторон)
- Шапка: задание, зафиксированная цена (крупно, не редактируется), стороны с телефонами (**раскрыты только теперь**) и кнопкой звонка.
- **Таймлайн-степпер статусов:** Подтверждено → Исполнитель выехал → Работа начата (гео-чекин: кнопка активна в радиусе 300 м от точки, иначе подтверждение заказчика) → Работа завершена (обязательно 1–6 фото результата) → Приёмка заказчика → Завершено. Каждый шаг — таймстамп, виден обеим сторонам.
- Приёмка: у заказчика 48 ч на «Принять» / «Есть проблемы» (→ спор). Молчание 48 ч → автоприёмка (обе стороны предупреждены заранее).
- Отмена после подтверждения: инициатор выбирает причину; исполнителю-отменщику — минус к рейтингу и пометка в профиле при рецидиве; заказчику — пометка «отменяет сделки» при рецидиве. Обеим сторонам — уведомления.
- После завершения: экран взаимной оценки (см. 2.13) + у заказчика кнопки «Нанять снова» и «В избранные исполнители».

## 2.12 Чат
- Список чатов: по сделкам (аватар, имя, превью, время, unread-бейдж) + чат поддержки закреплён сверху.
- Внутри: текст, фото (камера/галерея, сжатие), системные сообщения статусов сделки («Исполнитель отметил: работа начата»), реплай на сообщение, статусы доставлено/прочитано, индикатор «печатает…».
- Push при новом сообщении с quick-reply (Android) / прямо из уведомления (iOS).
- Пред-сделочные чаты закрываются через 72 ч неактивности; чат сделки живёт до завершения + 30 дней read-only.

## 2.13 Рейтинги и отзывы
- После завершения сделки обеим сторонам — экран оценки: 5 звёзд (обязательно) + чипы-теги (заказчику об исполнителе: «Пунктуально», «Аккуратно», «Техника в порядке», «Вежливо»; исполнителю о заказчике: «Чёткое ТЗ», «Оплата без проблем», «Подъезд как описан») + текст (опц., ≤500).
- Отзывы публикуются **одновременно после обеих оценок** либо через 7 дней (анти-месть, паттерн Airbnb). Ответ на отзыв — 1 раз, публично.
- Рейтинг профиля = среднее за последние 12 мес (свежесть важнее старых грехов), показываем «★4,8 · 36 оценок».
- Оценка ниже 3★ → необязательный вопрос «что пошло не так» (данные для модерации).

## 2.14 Уведомления
- **Центр уведомлений** (вкладка в «Сообщениях»): список с иконками типов, unread, «Прочитать все», тап → deep link на экран события. Хранение 90 дней.
- **Push-матрица (полная):**

| Событие | Кому | Канал |
|---|---|---|
| Новое задание по сохранённому фильтру | Исполнитель | push+центр |
| Новый отклик/контр-оффер | Заказчик | push+центр |
| Отклик принят/отклонён | Исполнитель | push+центр |
| Вашу ставку перебили | Исполнитель | push+центр |
| Аукцион: остался 1 час / 5 минут | Участники | push |
| Аукцион продлён (антиснайпинг) | Участники | центр |
| Аукцион завершён: вы победили / не победили | Участники | push+центр |
| Ожидает вашего решения (старт окна) + напоминание за 2 ч до конца окна | Заказчик | push+центр |

| Смена статуса сделки (каждый шаг) | Вторая сторона | push+центр |
| Напоминание о приёмке (24 ч из 48) | Заказчик | push |
| Новое сообщение в чате | Адресат | push |

- Настройки: тумблеры по группам (Аукционы / Сделки / Чат / Новые задания / Маркетинг). Маркетинг — opt-in. Тихие часы 22:00–08:00 для некритичных (кроме «перебили ставку» — по выбору пользователя).

# ЧАСТЬ 3. ВСТРОЕННЫЙ CRM И АНАЛИТИКА

> Философия: CRM — не отдельный продукт, а 5-й таб профиля каждой роли. Данные копятся сами из сделок — пользователь ничего не заполняет руками. Это главный магнит удержания: чем дольше работаешь через Traktor, тем ценнее твоя история.

## 3.1 CRM исполнителя — «Мой бизнес»
**Экран-дашборд (mobile: вертикальный скролл карточек; web: сетка 2–3 колонки).** Селектор периода сверху: Неделя / Месяц / Квартал / Год / Всё время / произвольный диапазон. Все виджеты пересчитываются под период.

**Виджеты (порядок сверху вниз):**
1. **Доход** — сумма завершённых сделок за период, крупно; рядом дельта к прошлому периоду («+18% к июлю» зелёным/красным); мини-график (bar chart по неделям/месяцам). Тап → детализация: список сделок с суммами.
2. **Воронка** — 4 ступени с числами и конверсиями: Просмотрено заданий → Сделано ставок/откликов → Выиграно → Завершено. Подсвечиваем узкое место («Вы выигрываете 8% ставок. Средний по платформе — 15%» + подсказка что улучшить: фото, рейтинг, скорость отклика).
3. **Загрузка техники** — по каждой единице: % занятых дней в периоде, доход на единицу, простой. Сигнал «Экскаватор простаивает 12 дней — снизьте минимальную ставку или расширьте радиус».
4. **Календарь занятости** — месяц-вид: дни с подтверждёнными сделками закрашены (тап → сделка), ручная блокировка дат «не работаю» (эти даты учитываются: система предупреждает при ставке на занятую дату).
5. **Клиентская база** — список всех заказчиков, с которыми были сделки: имя, число сделок, сумма всего, последняя сделка, ★. Сортировка по сумме/дате. Бейдж «Постоянный» (≥3 сделок). Тап → карточка клиента: история сделок, заметка (приватная, ≤500 симв. — «прораб Ашот, объект в Аване, платит сразу»), кнопки «Написать» и «Предложить услугу» (v2).
6. **Показатели качества** — рейтинг-динамика (график), среднее время отклика на задания, % отмен, теги из отзывов (облако: «Пунктуально ×12»).
7. **Экспорт** — «Скачать отчёт за период» → XLSX/PDF на почту или файлом (список сделок: дата, клиент, работа, техника, сумма, статус). Основа для налоговой отчётности исполнителя.

## 3.2 CRM заказчика — «Мои расходы»
1. **Расходы за период** — сумма, дельта, разбивка donut-диаграммой по категориям работ (земляные 60% / перевозка 30% / кран 10%). Тап по сегменту → сделки категории.
2. **Мои объекты** (лёгкая версия): при создании задания можно присвоить метку-объект («Дом в Дилижане», «Склад»); в CRM — фильтр расходов по объектам. Для прорабов это killer-feature: расходы по стройкам разложены сами.
3. **Избранные исполнители** — сохранённые + все, с кем работал: ★, сделки, суммы, приватная заметка; кнопка «Нанять снова» → предзаполненный визард задания с прямым приглашением этого исполнителя (задание видно только ему 6 часов, потом — всем).
4. **История заданий** — все задания со статусами и фильтрами; черновики; **«Повторить задание»** (клон визарда) — частая операция для регулярных работ (вывоз мусора, снег).
5. **Экономия на аукционах** — «Стартовая цена vs финальная: вы сэкономили 340 000 ֏ за год» (сильный retention-виджет, показывает ценность платформы).
6. **Экспорт** XLSX/PDF по сделкам (для компаний — бухгалтерия).

## 3.3 Правила дашбордов (UX аналитики)
- Каждый виджет: заголовок + одно число крупно + сравнение с прошлым периодом + мини-график. Не более 7 виджетов на дашборд.
- Пустые данные → виджет показывает мотивирующий empty state («Завершите первую сделку — здесь появится доход»), не нули.
- Графики: библиотека fl_chart; тултип по тапу; без легенд, где можно подписать напрямую; цвета из палитры 1.7; в тёмной теме — те же графики, проверенные на контраст.
- Все расчёты — Cloud Functions с агрегатами (коллекция `stats_daily` на пользователя: дата, доход, сделки, ставки…), клиент не пересчитывает историю на лету.
- Числа анимируются (count-up 400 мс) — дашборд «живой».

# ЧАСТЬ 4. АДМИН-ПАНЕЛЬ, WEB, НФТ, ПРИЁМКА

## 4.1 Админ-панель (Flutter Web, отдельный вход, роли admin/moderator)
1. **Дашборд платформы:** DAU/WAU, новые регистрации по ролям, задания (создано/завершено), GMV (сумма завершённых сделок), конверсия задание→сделка, средний чек, топ-категории, карта активности по регионам.
2. **Очередь верификации техники:** список pending, карточка: фото + документы рядом (zoom), кнопки Одобрить / Отклонить (обязательная причина из справочника + свой текст). SLA-таймер «висит 18 ч» с сортировкой по возрасту.
3. **Пользователи:** поиск по телефону/имени/ID, карточка: активность, сделки, жалобы; действия: предупреждение (шаблоны), заморозка ставок, бан (с причиной, обратимый), удаление контента.
4. **Споры:** очередь, карточка спора: вся сделка (чат, фото чекинов, таймлайн), переписка со сторонами внутри спора, решение (в пользу А/Б/компромисс) с обязательным обоснованием — уходит обеим сторонам.
5. **Каталог:** CRUD категорий и specTemplate (без релиза приложения — каталог в Firestore), порядок, иконки, локализации названий.
6. **Жалобы на контент/пользователей:** очередь с контекстом, действия.
7. **Пуш-кампании (v2):** сегмент (роль, регион, активность) + текст + ссылка. Только для admin, не moderator.
8. Журнал действий админов (кто/что/когда) — обязателен.

## 4.2 Web-специфика клиентского приложения
- Одна кодовая база Flutter Web; макеты по breakpoints 1.8. Desktop: лента слева (список) + карта справа; деталка задания — центральная колонка 720 px; аукцион — двухколоночный (ставки слева, панель ставки справа sticky).
- **Публичные страницы без логина** (SEO + шеринг): деталка задания (без точного адреса), профиль исполнителя, лендинг. Мета-теги OG (превью в мессенджерах — критично для сарафана), sitemap, hreflang для 3 языков. Если SEO Flutter Web окажется недостаточным — статичный пререндер публичных страниц Cloud Function'ом (заложить в архитектуру).
- Клавиатура: Enter — сабмит форм, Esc — закрыть модал; фокус-обводки видимы.
- Web-push (FCM) — запрашивать только после первого значимого действия, не на входе.

## 4.3 Нефункциональные требования
- **Производительность:** холодный старт ≤2,5 с на среднем Android; TTI web ≤3 с на 4G; ленты 60 fps; фото — прогрессивная загрузка (blur-hash плейсхолдеры).
- **Реалтайм аукциона:** задержка отображения чужой ставки ≤2 с; серверное время — источник истины (клиентский таймер синхронизируется, дрейф корректируется); финиш и выбор победителя — только Cloud Function (клиенту не доверяем).
- **Целостность ставок:** транзакции Firestore (две одновременные ставки — детерминированный порядок); идемпотентность (двойной тап ≠ две ставки).
- **Безопасность:** Firestore Security Rules — доступ только к своим данным; телефоны не читаемы до статуса сделки «Подтверждено»; reserve-цена не читаема клиентами вообще (только Functions); rate limiting на ставки (≤1/сек) и создание заданий (≤10/день); App Check против ботов.
- **Приватность:** согласие на гео с объяснением зачем; удаление аккаунта = анонимизация профиля с сохранением обезличенной истории сделок (целостность рейтингов); политика конфиденциальности hy/ru/en.
- **Оффлайн:** просмотр кэша лент и сделок; создание черновиков офлайн с синхронизацией; ставки офлайн запрещены (честность аукциона) — понятное сообщение.
- **Продуктовая аналитика (события):** signup_completed, role_selected, equipment_added, equipment_approved, job_draft_started, job_published(mode), job_viewed, offer_sent(type), bid_placed, bid_outbid, auction_won, auction_declined_by_client, deal_confirmed, deal_completed, review_left, chat_message_sent, crm_opened, export_downloaded, push_opened(type). Воронки: публикация задания (по шагам визарда), ставка, сделка.
- **Тестирование:** unit на бизнес-логику (скоринг, валидации ставок, статусные переходы), widget-тесты ключевых экранов, integration-тест сценария «создать задание → ставка → победа → подтверждение → завершение → отзыв»; ручной чек-лист на iOS/Android/Web перед каждым релизом.

## 4.4 Матрица статусных переходов задания (защита от гонок)
```

collecting_offers → deal_pending (заказчик выбрал) → confirmed
bidding → deciding (дедлайн, есть ставки ≥ reserve) → confirmed | declined_all | expired(молчание)
bidding → expired_no_bids (нет ставок) → можно перезапустить (клон)
confirmed → in_progress → work_done → completed | disputed
disputed → resolved(→completed | cancelled)
Любой активный статус → cancelled (с фиксацией инициатора и причины)
```
Все переходы — только через Cloud Functions с проверкой прав и текущего статуса (клиент шлёт intent, сервер решает).

# ЧАСТЬ 5. РАСШИРЕНИЕ v1.1 — АРЕНДА ТЕХНИКИ, ПЕРЕВОЗКИ А→Б, РАЗНОРАБОЧИЕ
*(утверждено Тиграном 13.08.2026; логика продумана по полному циклу обеих ролей)*

## 5.1 Четыре типа заказа
FAB «+» заказчика открывает bottom sheet выбора типа (поле `orderType` в модели):

| Тип | Суть | Ценообразование |
|---|---|---|
| `job` | Задание с описанием (части 1–4: фикс-цена / обратный аукцион) | цена за результат |
| `rental` | Аренда техники без задания — почасовая / посменная / посуточная | тариф × время + подача |
| `transport` | Перевозка А→Б грузовиком («что отвезти») | подача + ֏/км (+ грузчики) |
| `workers` | Разнорабочие без техники | ֏/чел/час × кол-во × часы |

Опция «разнорабочие» доступна как ДОПОЛНЕНИЕ внутри любого из первых трёх типов (§5.5).

## 5.2 Аренда техники (rental)
**Тарифы** задаёт исполнитель в карточке каждой единицы (новые поля визарда техники, шаг 2):
- ֏/час (+ минимальный заказ, по умолчанию 3 ч), ֏/смена (8 ч), ֏/сутки;
- подача на объект: фикс ֏ или ֏/км (по расстоянию до объекта);
- v1 — аренда всегда С ОПЕРАТОРОМ (машинист исполнителя). Без оператора — v2 (залог, проверка прав, страховка) — заложить флаг в модель.

**Флоу заказчика:** техника (поиск §2.х «Техника» / чужой профиль / избранное) → кнопка «Арендовать» →
дата + время начала → длительность (переключатель Часы/Смена/Сутки + степпер) → адрес объекта (карта-пин)
→ опции (разнорабочие §5.5) → **прозрачный расчёт построчно** (аренда + подача + рабочие = итого)
→ «Запросить бронь». Прямо в форме показываем ближайшие свободные слоты исполнителя
(«сегодня после 13:00 — свободен ✓») — заказчик не тратит время на занятую технику.

**Флоу исполнителя:** push «Запрос брони» → экран запроса: заказчик (рейтинг), период, адрес,
опции, моя выручка; строка проверки календаря («свободно до 20:00 ✓» / «конфликт с бронью 16:00 ⚠»).
Действия: **Подтвердить** / **Предложить другое время** (выбор слотов из своего календаря, заказчику
уходит встречное предложение) / **Отклонить** (причина по желанию). Подтверждение = Deal type=rental,
период блокируется в календаре CRM автоматически.

**Сделка-аренда:** статусы Подтверждена → Техника выехала → Работает → Завершена → Приёмка → Отзывы
(та же цветовая карта §1.10). В активной сделке — **живой счётчик оставшегося оплаченного времени**
+ прогресс-бар периода. Push обеим сторонам «остался 1 час брони».

**Отмена брони:** бесплатно ≥ 24 ч до старта; позже — пометка в профиле инициатора (рецидив виден),
второй стороне вежливый push. **Простой по вине заказчика** (техника приехала и ждёт): исполнитель
жмёт «Начать ожидание» — счётчик простоя по тарифу ½ часового, заказчик видит его в реальном времени
(никаких сюрпризов при расчёте).

## 5.3 Продление аренды (ключевая фича)
Заказчик не успел за забронированное время — продлевает НЕ выходя из приложения:
1. Кнопка «Продлить» в сделке-аренде: чипы **+1 ч / +2 ч / +4 ч / +сутки / своё**; цена доплаты сразу.
2. Система проверяет календарь исполнителя: следом бронь → показываем максимум
   («Карен свободен до 20:00 — максимум +3 ч»).
3. Запрос → исполнителю push → подтверждение одним тапом → доплата отдельной строкой в смете сделки
   (`Transaction.type=rental_extension`), итог пересчитан, календарь продлён.
4. **За 1 час до конца брони** заказчику push «Успеваете? Продлить можно заранее» — продление заранее,
   а не скандал на объекте.
5. Продлить нельзя (у исполнителя следующая бронь) → сразу предлагаем свободную технику той же
   категории рядом («перехват»: новая бронь продолжением работ, мини-карточки кандидатов).

## 5.4 Перевозка А→Б (transport)
Быстрый флоу (НЕ 5-шаговый визард — заказ грузовика должен занимать < 1 минуты):
- **Точка А** (погрузка) и **Точка Б** (выгрузка): адреса с автодополнением + пины на карте;
  маршрут и километраж считаются автоматически. Опция «несколько рейсов ×N».
- **Груз:** тип чипами (стройматериалы / сыпучие / мебель / техника / мусор / другое), примерный вес
  и объём, фото груза (сильно снижает споры), «нужны грузчики» → §5.5.
- **Когда:** «Как можно скорее» — push ближайшим свободным грузовикам подходящей грузоподъёмности,
  отклики в реальном времени (режим ожидания как в такси); или «Ко времени».
- **Цена:** ориентир = подача категории + ֏/км × км (+ грузчики); заказчик принимает ориентир или
  ставит свою; исполнители принимают или предлагают контр-цену (1 раунд, §2.10).
- **Статусы сделки:** Выехал на погрузку → Погрузка → В пути → Выгрузка → Завершено
  (тайм-стемпы, видят обе стороны). Гео-трек рейса на карте — v2.
- **Платное ожидание:** первые 30 мин на погрузке/выгрузке включены; далее ֏/15 мин по тарифу
  категории — счётчик в сделке виден обеим сторонам в реальном времени.
- **Edge:** груз больше заявленного → исполнитель отмечает «нужен доп. рейс / пересчёт», заказчик
  подтверждает в приложении (фиксация в сделке вместо спора на месте).

## 5.5 Разнорабочие (workers)
- **Опция в любом заказе** (задание / аренда / перевозка): галочка «Нужны разнорабочие» + количество
  (1–10) + часы. В карточке задания исполнителям видно «+3 рабочих».
- **Кто даёт людей:**
  (а) исполнитель техники своей бригадой — новые поля техники «Бригада: до N чел, ֏/чел/час»;
  наличие бригады учитывается в скоринге соответствия;
  (б) отдельная категория каталога «Разнорабочие» — заказ людей без техники: кол-во, часы, описание
  работы, ставка ֏/чел/час (подсказка рыночной), итог; откликаются бригадиры.
- **Чекин по людям:** при старте работ заказчик подтверждает фактическое число пришедших
  («пришло 2 из 3») — цена пересчитывается автоматически. Защита обеих сторон.
- Инструмент: галочка «нужен свой инструмент» (лопаты/кувалды) в заказе рабочих.

## 5.6 Изменения модели данных и пушей
```
Deal.type        [job|rental|transport|workers]
Rental      {unitId, startAt, durationH, unit[hour|shift|day], rate, deliveryFee,
             extensions[{addH, price, confirmedAt}], idle[{startAt, min, price}], operatorIncluded:true}
Transport   {from{geo,addr}, to{geo,addr}, km, trips, cargo{type, weightT, volumeM3, photos[]},
             waiting[{stage[load|unload], min, price}], extraTripRequested?}

Equipment.rates {hourly, shift8h, daily, minHours, deliveryFee|perKm}
Equipment.crew  {maxCount, pricePerHour}           // бригада исполнителя

```
Новые push-события: запрос брони · бронь подтверждена / отклонена / встречное время ·
остался 1 час брони (обеим) · запрос продления · продление подтверждено / невозможно (+кандидаты) ·
простой начат · грузовик: принял / на погрузке / ожидание платное / доп. рейс.

Индексы: bookings по (unitId, startAt); свободность техники — из календаря CRM (§3.1.4).

## 5.7 Приёмка v1.1 (дополнение к §4.5, этап 2)
Сквозные сценарии приёмки: (1) бронь → подтверждение → работа → **продление** → завершение → отзывы;
(2) перевозка А→Б с грузчиками и платным ожиданием; (3) заказ разнорабочих с чекином «пришло 2 из 3»;
(4) конфликт календаря → встречное время; (5) отмена брони за <24 ч с пометкой.

# ЧАСТЬ 6. АРХИТЕКТУРА СИСТЕМЫ (v1.2, 13.08.2026)

Полный архитектурный документ — **docs/arhitektura-v1.md** (15 ADR с обоснованиями и отклонёнными альтернативами), визуальная карта — **design/architecture-map.html**. Здесь — обязательная выжимка:

1. **Мультисервисная архитектура, НЕ монолит:** 9 доменных сервисов по DDD bounded contexts (identity · catalog · orders · auction · deals · chat · notifications · media · reporting) + admin-BFF + API-gateway. Каждый сервис деплоится независимо, владеет своей схемой данных эксклюзивно; cross-schema JOIN запрещён; общение — только API + события.
2. **Клиенты — Flutter (все 4 приложения), бэкенд — Go** (ADR-1: серверного Flutter не существует; Go выбран за WS-производительность аукциона и найм).
3. **Данные:** PostgreSQL 16 + PostGIS — источник истины (schema-per-service); Redis — кэш/лимиты; R2 — медиа; Typesense — поиск. Брони аренды защищены exclusion-constraint на уровне БД — перекрытие физически невозможно.
4. **События:** transactional outbox → Pub/Sub, идемпотентные консьюмеры, DLQ. Реестр схем событий в монорепо.
5. **Realtime:** Centrifugo (каналы аукциона/чата/пользователя, recovery, server_time в каждом кадре); push — FCM.
6. **Аукцион:** advisory-lock + append-only журнал ставок + серверный timer-wheel + антиснайпинг в транзакции ставки; скоринг и финиш — только сервер.
7. **Инфраструктура:** GCP Cloud Run (Frankfurt) + Cloudflare Edge; Terraform; среды dev/stage/prod; канареечные релизы; OpenAPI-кодоген Dart-клиента; OTel → Grafana, Sentry. SLO: p95 API < 300 мс, доставка ставки < 2 с.
8. **Стоимость:** MVP ~$150–250/мес; фазы масштабирования и «пути эвакуации» от каждого vendor — §10–11 архитектурного документа.

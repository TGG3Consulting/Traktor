# Traktor — Архитектура системы v1.0
### Мультисервисная архитектура маркетплейса заданий и аренды техники
**Дата:** 13.08.2026 · **Статус:** на утверждении Тиграна · **Основание:** ТЗ v1.1 (части 1–5)
**Принцип документа:** каждое решение — с обоснованием и отклонёнными альтернативами, чтобы через год не было «а тут не додумали».

---

## 0. Резюме для владельца (1 минута)

Система разбивается на **9 независимых сервисов** по границам бизнес-доменов (DDD bounded contexts) + edge-слой Cloudflare + событийная шина. Клиенты (iOS, Android, Web, админка) — **Flutter, единая кодовая база**. Бэкенд — **Go** (не Dart: см. ADR-1). Облако — **GCP Cloud Run** (контейнеры, без vendor lock — см. ADR-2). База — **PostgreSQL 16 + PostGIS** (не Firestore — см. ADR-4, это пересмотр §1.5 ТЗ). Файлы — **Cloudflare R2 + CDN**. Realtime аукциона и чата — **Centrifugo (WebSocket)**. Push — **FCM**. Стоимость MVP-инфраструктуры: **~$150–250/мес**.

Это НЕ монолит и НЕ «микросервисный зоопарк из 30 сервисов»: 9 сервисов — столько, сколько реально разных доменов в ТЗ, каждый деплоится и масштабируется отдельно, общаются только через API и события.

## 1. Главные принципы (чем руководствуемся при любом спорном вопросе)

1. **Сервер — источник истины.** Клиенту не доверяем ничего: время, ставки, статусы, цены считает сервер (ТЗ §4.3). Клиентский таймер — только отображение с синхронизацией.
2. **Границы по доменам, не по таблицам.** Сервис владеет своими данными эксклюзивно; чужие данные — только через API/события. Запрещены cross-schema JOIN'ы — это то, что превращает «микросервисы» в распределённый монолит.
3. **События — через transactional outbox.** Никаких двойных записей «в базу и в шину»: запись в outbox в той же транзакции, релей доставляет в шину. Каждый консьюмер идемпотентен.
4. **Деньги и брони — только с гарантиями БД.** Перекрытия броней исключает сама Postgres (exclusion constraint), деньги v2 — двойная запись (ledger). Никакой «проверки в коде», которую можно обойти гонкой.
5. **Идемпотентность всех мутаций.** `Idempotency-Key` на каждый POST: двойной тап ≠ две ставки (ТЗ §4.3).
6. **Портируемость важнее удобства облака.** Всё в контейнерах + Terraform; используем управляемые сервисы GCP, но каждый имеет заранее записанный «путь эвакуации» (§10).
7. **Масштабируемся фазами, не заранее.** Архитектура допускает рост до сотен тысяч пользователей, но в фазе MVP не платим за то, чего нет (§11).

## 3. Ключевые решения (ADR — Architecture Decision Records)

### ADR-1. Flutter — только клиенты; бэкенд — Go
**Контекст.** «Всё на Flutter» корректно означает: все ЭКРАНЫ на Flutter — iOS, Android, Web и админ-панель из одной кодовой базы (это и было в ТЗ). Бэкенд на Flutter не пишется в принципе; на Dart — можно (Serverpod, dart_frog), но экосистема серверного Dart незрелая: нет боевых библиотек уровня Kafka-клиентов, слабый опыт индустрии, некого нанимать.
**Решение.** Бэкенд — **Go 1.23+**: один статический бинарник на сервис, лучшая в классе производительность WebSocket/конкурентности (критично для аукциона), простой найм, огромная экосистема (pgx, NATS, OTel).
**Отклонено.** Dart на сервере (экосистема), Node/NestJS (медленнее и прожорливее под WS-нагрузкой аукционов, но допустим как замена, если команде ближе TypeScript — архитектура от языка не зависит), Java/Kotlin (тяжёлый рантайм для Cloud Run cold start).

### ADR-2. Облако — GCP Cloud Run; регион Frankfurt; всё в контейнерах + Terraform
**Контекст.** До Армении ближайшие серьёзные регионы — Франкфурт (GCP europe-west3, AWS eu-central-1): ~60–90 мс RTT до Еревана — комфортно для API; интерактив сглаживается edge-кэшем Cloudflare.
**Решение.** **Cloud Run** (serverless-контейнеры): нулевой DevOps в MVP, scale-to-zero для фоновых сервисов, канареечные ревизии из коробки. Вся инфраструктура — **Terraform** (среды dev/stage/prod из одного кода).
**Отклонено.** Kubernetes (GKE) — на старте это налог ~20% времени команды без выгоды; путь миграции Cloud Run→GKE тривиален (те же контейнеры). AWS — эквивалентен, выбран GCP из-за более простого serverless и нативного FCM/Firebase-инструментария. Hetzner/VPS — дешевле, но БД, бэкапы, безопасность на себе; вариант для фазы оптимизации затрат (§11), не для старта.

### ADR-3. 9 сервисов по bounded contexts — не монолит и не зоопарк
**Решение.** Сервис на каждый реальный домен ТЗ (§4). Отдельный деплой, отдельный владелец данных.
**Почему не монолит:** разная нагрузка и характер (аукцион — пиковый WS-realtime; медиа — throughput; CRM — фоновые агрегаты); независимые релизы; отказ одного не роняет всё (упал chat — ставки идут).
**Почему не 25 сервисов:** каждый лишний сервис = +деплой, +мониторинг, +сетевые сбои. Дробим только там, где разные данные, нагрузка или ритм изменений.

### ADR-4. PostgreSQL 16 + PostGIS вместо Firestore (пересмотр ТЗ §1.5)
**Контекст.** ТЗ v1.0 фиксировало Firebase/Firestore. При проектировании мультисервисной системы Firestore как ядро не выдерживает критики: (а) аукцион требует сериализуемых транзакций и сложных инвариантов — в Firestore это боль; (б) брони аренды требуют constraint'ов на перекрытие интервалов — Firestore не умеет; (в) CRM-отчёты = аналитические запросы — Firestore дорог и неудобен (плата за каждое чтение, нет агрегаций); (г) PostGIS решает гео-ленту нативно; (д) стоимость Firestore при росте непредсказуема.
**Решение.** **PostgreSQL 16 + PostGIS** — источник истины. Физически в MVP — один инстанс Cloud SQL, логически — **schema-per-service** с изоляцией правами доступа (у каждого сервиса своя роль, видит только свою схему). Разъезд по отдельным инстансам — прозрачный (меняется только DSN).
**Firebase остаётся** там, где он лучший: **FCM (push), Crashlytics, Analytics (клиентские события), Remote Config (фиче-флаги клиента)**. Firebase Auth уходит (см. ADR-6).
**Ключевой инвариант броней (то, что «не додумывают»):**
```sql
-- Перекрытие двух броней одной техники невозможно ФИЗИЧЕСКИ, не «проверкой в коде»:
ALTER TABLE booking ADD CONSTRAINT no_overlap
  EXCLUDE USING gist (unit_id WITH =, period WITH &&) WHERE (status IN ('confirmed','active'));
-- period = tstzrange(start_at, end_at). Продление = UPDATE расширяющий range в той же гарантии.
```

### ADR-5. Шина событий — Pub/Sub через transactional outbox
**Решение.** Каждый сервис пишет доменные события в свою таблицу `outbox` в той же транзакции, что и данные; релей (Cloud Run job / sidecar) публикует в **GCP Pub/Sub**; консьюмеры идемпотентны (`processed_events` по event_id). Схемы событий — версионируемый реестр (JSON Schema в монорепо, CI-проверка совместимости).
**Отклонено.** Kafka — оверкилл до десятков тысяч событий/сек (путь миграции записан); прямые HTTP-вызовы между сервисами для доменных фактов — создают связность и каскадные отказы. Синхронные вызовы разрешены только для запросов «здесь и сейчас» (например, проверка календаря при продлении).

### ADR-6. Аутентификация — собственный identity-сервис + Dexatel OTP
**Решение.** Подтверждаем решение от 13.08: OTP через **Dexatel Verify API**; identity-сервис выпускает **JWT access (15 мин, ES256) + rotating refresh (30 дней, привязка к устройству, reuse-detection)**. Публичные ключи — JWKS-эндпоинт, все сервисы проверяют токен локально (без похода в identity). App Check заменяем на **Play Integrity / App Attest** проверяемые identity-сервисом.
**Роли в токене:** client/owner/admin/moderator + activeRole. Телефоны в БД — шифрование на уровне колонки (pgcrypto), раскрытие второй стороне только при статусе сделки ≥ confirmed (проверка на уровне deals-API, не клиента).

### ADR-7. Realtime — Centrifugo; push — FCM
**Контекст.** Требование ТЗ: чужая ставка видна ≤ 2 с (§4.3).
**Решение.** **Centrifugo** (боевой open-source WS-сервер, k8s-ready, JWT-каналы, presence, история): каналы `auction:{jobId}` (ставки, продления таймера), `chat:{dealId}`, `user:{userId}` (личные события), `deal:{id}` (статусы). Сервисы публикуют в Centrifugo по HTTP-API из консьюмеров событий. Мобильный клиент: один WS-коннект, мультиплекс подписок, авто-reconnect с recovery (Centrifugo отдаёт пропущенное из истории канала).
**Отклонено.** Свой WS-сервер (изобретение велосипеда: presence, recovery, масштабирование уже решены), Firestore-listeners (см. ADR-4), polling (не 2 с).

### ADR-8. Медиа — Cloudflare R2 + прямая загрузка + пайплайн обработки
**Решение.** Клиент сжимает фото (isolate, ≤1600px, WebP q80 — как в ТЗ) → media-сервис выдаёт **presigned PUT в R2** (клиент грузит напрямую, минуя наш бэкенд) → событие → воркер: EXIF-strip (приватность!), thumbnails (3 размера), **blur-hash** (плейсхолдеры из ТЗ §4.3), **pHash-дедупликация** (ловим чужие фото техники из интернета — ТЗ §2.5). Отдача — через Cloudflare CDN (`media.traktor.am`), горячие трансформации — Cloudflare Image Resizing.
**Почему R2, а не S3:** нулевой egress-трафик (S3 берёт $0.09/GB за отдачу — для фото-тяжёлого маркетплейса это главный счёт), S3-совместимый API (уйти на S3/MinIO — смена endpoint'а).

### ADR-9. Аукцион — Redis-состояние + Postgres-журнал + серверные таймеры
**Решение (самый нагруженный домен):**
- Ставка: `POST /bids` с Idempotency-Key → advisory-lock по jobId → валидации (ниже лучшей; ≥30% старта; шаг; активная техника; календарь §5) → INSERT append-only + UPDATE текущего лидера + outbox(BidPlaced) — одна транзакция ≤ 10 мс.
- Redis: ZSET лидерборда и кэш состояния аукциона — только производное от Postgres (пересоздаваемо), для мгновенных чтений ленты ставок.
- **Таймеры финиша — в самом сервисе**: in-memory timer-wheel + персистентная таблица `auction_deadlines`; при рестарте — восстановление из таблицы; страховка — сторожевой тик каждые 30 с (Cloud Scheduler) добирает просроченные. Антиснайпинг (+10 мин) = UPDATE deadline в транзакции ставки.
- Финиш: скоринг (0.6/0.25/0.15 из ТЗ) считается сервером, reserve-цена хранится зашифрованной, никогда не отдаётся в API списков.
- Серверное время: клиент получает `server_time` в каждом WS-сообщении и корректирует дрейф отображаемого таймера (ТЗ §4.3).

### ADR-10. Сделки — явная стейт-машина + сага-оркестрация событиями
**Решение.** Матрица переходов ТЗ §4.4 (+ аренда/перевозка §5) — это код: таблица `transitions(from,to,role,guard)`; любой переход — только через deals-API с проверкой прав и текущего статуса. Межсервисные последствия (заблокировать календарь, открыть телефоны, создать чат, начислить строку сметы) — реакции на события DealConfirmed, RentalExtended и т.д. **Temporal** (workflow-движок) сознательно отложен до v2-эскроу: пока стейт-машина + идемпотентные консьюмеры покрывают всё дешевле.

### ADR-11. API — REST/OpenAPI + кодоген Dart-клиента; версия /v1
**Решение.** Публичный API — REST/JSON по **OpenAPI 3.1** (single source of truth в монорепо): из него генерируются Dart-клиент (dio + retrofit-стиль), Go-серверные интерфейсы и документация. Пагинация — курсорная. Ошибки — RFC 9457 (problem+json) с человекочитаемыми `detail` для тостов из ТЗ. gRPC между сервисами отложен: HTTP/JSON внутри + события покрывают нагрузку MVP с запасом; ревизит при p95 межсервисных вызовов > 50 мс.

### ADR-12. Карты — MapLibre + OSM-тайлы вместо Google Maps (пересмотр ТЗ §1.5)
**Контекст (то, о чём жалеют на масштабе).** Google Maps SDK бесплатен на мобильных для отображения, но: Dynamic Maps на **Web** — платные с первого рендера сверх квоты, геокодинг платный ($5/1000), автодополнение платное, и главное — привязка навсегда.
**Решение.** **MapLibre GL** (Flutter-плагин maplibre_gl) + тайлы **Protomaps/OpenFreeMap** (self-host на R2 — единицы $ в месяц, покрытие Армении отличное в OSM). Геокодинг/автодополнение: self-hosted **Photon** (OSM) как основной + платный fallback (Google Geocoding) фиче-флагом для адресов, которые Photon не взял. Пины, кластеры, радиусы — нативно в MapLibre.
**Экономика:** при 50k MAU Google-стек стоил бы сотни $/мес; наш — ~$10.

### ADR-13. Поиск и лента — PostGIS + Typesense
**Решение.** Гео-радиус, сортировка «ближе», кластеры пинов — **PostGIS** (`ST_DWithin`, geohash-индексы). Текстовый поиск (название/описание/марка, опечатки, армянская+русская морфология), фасеты фильтров — **Typesense** (лёгкий, один бинарник, e2-small): индексация консьюмером событий JobPublished/EquipmentApproved. Подписки на фильтры (ядро retention, ТЗ §2.7): matcher-консьюмер прогоняет каждое новое задание по сохранённым фильтрам (обратный поиск) → notifications.
**Отклонено.** Elasticsearch (тяжёлый и дорогой для MVP), «поиск в Postgres LIKE» (не переживёт армянско-русскую морфологию и опечатки).

### ADR-14. Наблюдаемость — OpenTelemetry + Grafana Cloud + Sentry
**Решение.** Все сервисы — OTel SDK (трейсы, метрики, логи, единый trace-id от клиента до БД); бэкенд — Grafana Cloud free-tier на старте (Tempo/Loki/Prometheus); клиент — Sentry (Flutter) + Crashlytics. **SLO фиксируем сразу:** p95 API < 300 мс; доставка ставки по WS < 2 с (метрика end-to-end, требование ТЗ); доставка push < 10 с; аптайм ядра 99.5% (MVP) → 99.9% (после запуска). Алерты — на burn-rate error budget, не на каждый чих.

### ADR-15. Безопасность и приватность — по чек-листу §9
JWT ES256 + JWKS, Play Integrity/App Attest, rate-limit на edge (Cloudflare) И в сервисах (Redis, лимиты ТЗ: ставки ≤1/с, задания ≤10/день), шифрование телефонов, PII-минимизация в логах (авто-редакция), секреты в Secret Manager, бэкапы PITR + еженедельный restore-тест, аудит админ-действий append-only (требование ТЗ §4.1.8), удаление аккаунта = анонимизация (ТЗ §4.3).

## 5. Ключевые потоки (последовательности)

**Ставка в аукционе (требование ≤ 2 с):**
клиент → gateway (JWT, Idempotency-Key) → auction: advisory-lock(jobId) → валидации (цена/шаг/30%/техника approved/календарь свободен — запрос в deals по gRPC-интерфейсу «свободна ли дата», ответ из кэша) → txn{INSERT bid; UPDATE leader; антиснайпинг: если now > deadline−5м → deadline+=10м; outbox} → 200 (optimistic UI клиента подтверждён) → релей → Pub/Sub → консьюмеры: notifications (push «перебили» предыдущему лидеру с учётом тихих часов-исключения), centrifugo-паблиш `auction:{id}` (новая ставка+server_time+new_deadline) → все подписанные клиенты обновились. Целевой бюджет: запись ≤ 50 мс, доставка ≤ 1 с.

**Продление аренды (§5.3 ТЗ):**
клиент «+2 ч» → deals: читает booking, СИНХРОННО проверяет соседнюю бронь (та же схема, тот же сервис — без сетевого вызова), считает максимум и цену → создаёт extension-request (pending) → событие → push исполнителю → исполнитель «подтвердить» → deals: txn{UPDATE booking.period (exclusion constraint гарантирует непересечение!); строка сметы; outbox RentalExtended} → уведомления обеим, Centrifugo обновляет счётчик на экране заказчика. Отказ/невозможность → deals отдаёт кандидатов «перехвата»: запрос в catalog+search (свободная техника категории рядом).

**Перевозка «как можно скорее» (§5.4):**
orders: TransportRequested → matcher (в составе search): PostGIS-кандидаты (радиус, грузоподъёмность ≥ веса, статус free) → notifications: fanout push топ-N водителям волнами (5 ближайших, через 60 с — следующие 5) → отклики через auction-сервис (offers) → клиент видит их realtime в `transport:{id}` → выбор → DealConfirmed.

**Чекин рабочих «пришло 2 из 3» (§5.5):** deals: событие чекина с фактом → пересчёт сметы в той же транзакции → обе стороны видят новую смету (Centrifugo) + запись в аудит сделки.

**Финиш аукциона:** timer-wheel → auction: txn{скоринг всех активных ставок; отсев ниже reserve; статус deciding; outbox AuctionFinished(winner, top)} → deals создаёт «окно решения 12 ч» (свой таймер) → молчание → авто-закрытие + вежливые уведомления (ТЗ §2.9).

## 7. Клиентская архитектура (Flutter — все 4 приложения)

**Монорепо (melos), пакеты:**
```
apps/    mobile (iOS+Android) · web · admin
packages/ design_system (токены §1.7–1.8 ТЗ, UI-kit §1.10)
          api_client (кодоген из OpenAPI — руками не пишется)
          realtime (Centrifugo-клиент: reconnect, recovery, мультиплекс)
          domain_* (модели и правила по доменам — зеркалят bounded contexts)
          l10n (ARB hy/ru/en) · analytics · offline_cache
```
**Слои фичи:** presentation (виджеты) → application (Riverpod-нотифаеры, состояния loading/content/empty/error/offline §1.11) → data (репозитории: api_client + offline_cache). Навигация — go_router, deep links `/job/{id}` и пр.
**Offline (§4.3 ТЗ):** Drift (SQLite) — кэш лент/сделок с отметкой времени; очередь исходящих черновиков; ставки офлайн запрещены на уровне репозитория с человекочитаемой ошибкой.
**Realtime-дисциплина:** один WS на приложение; подписки привязаны к жизненному циклу экрана; server_time-коррекция таймеров; optimistic UI ставок с откатом (ТЗ §2.9).
**Загрузка фото:** compress в isolate → presigned PUT → progress → blur-hash превью сразу.
**Качество:** golden-тесты design_system (светлая/тёмная, 3 локали, шрифт 130%), widget-тесты ключевых экранов, интеграционный сценарий ТЗ §4.3 в Firebase Test Lab / физические устройства. Админка — тот же design_system, отдельный роутинг/深линки не нужны.

## 8. Инфраструктура и DevOps

- **Монорепо** (сервисы Go + Flutter + Terraform + OpenAPI + JSON Schema событий) — атомарные изменения контрактов.
- **CI (GitHub Actions):** lint → unit → контрактные тесты (OpenAPI-диффы против breaking changes, совместимость схем событий) → сборка контейнеров (distroless) → trivy-скан → deploy в dev; в prod — вручную подтверждаемый канареечный деплой (Cloud Run traffic split 5%→50%→100% с авто-откатом по метрикам).
- **Среды:** dev (scale-to-zero, дешёвая) / stage (продовые настройки, синтетические данные) / prod. Секреты — Secret Manager, доступ по Workload Identity (никаких ключей в env-файлах).
- **Фиче-флаги:** серверные — таблица в identity+gateway (kill-switch на любую фичу: «отключить аукционы» без релиза); клиентские — Remote Config (вход через Telegram-бот и пр.).
- **Нагрузочное тестирование до запуска:** k6-сценарий «100 конкурентных ставок в один аукцион» и «1000 одновременных WS» — обязательный gate релиза этапа 3 (ТЗ §4.5).

## 9. Безопасность (чек-лист)

Слои: Cloudflare WAF+bot management+rate-limit → gateway (JWT, схема-валидация, Idempotency) → сервисные проверки прав (владение ресурсом, роль, статус) → БД (роли по схемам, шифрование PII).
Особые точки из ТЗ: reserve-цена — только в auction-схеме, шифрована, нет в API; телефоны — раскрытие гейтится статусом сделки на сервере; маскирование контактов в пред-сделочном чате — фильтр в chat-сервисе (regex+нормализация, мягкое предупреждение); анти-фрод ставок: velocity-правила (Redis), shadow-ban песочница для подозрительных; админ-действия — append-only аудит; DSR (запрос/удаление данных) — процедура анонимизации по всем схемам через событие UserDeleted.

## 11. Фазы масштабирования и стоимость

**Фаза 0 — разработка (сейчас):** dev-среда scale-to-zero. ~$50/мес.
**Фаза 1 — запуск (до ~10k MAU):** всё по этому документу: 1×Cloud SQL (2 vCPU), 1×Redis 1GB, Cloud Run min-instances=1 для auction/gateway/centrifugo (без cold start), остальное scale-to-zero. **~$150–250/мес** (+SMS по объёму, ~15–25 ֏/шт через Dexatel).
**Фаза 2 — рост (10–100k MAU):** read-реплика Postgres; вынос auction и deals на отдельные инстансы БД; BigQuery-аналитика; Centrifugo ×2 + Redis-брокер; CDN-правила агрессивнее. ~$600–1200/мес.
**Фаза 3 — масштаб (100k+):** Kafka вместо Pub/Sub при >50k событий/с, шардирование по регионам при экспансии за Армению (архитектура это допускает: currency в деньгах, TZ в датах, языки — с первого дня по ТЗ).
**Правило:** ни один пункт фазы 2–3 не строится в фазе 1. Всё, что нужно, — уже заложено интерфейсами.

## 12. Риски и «недодумки», закрытые этим документом

1. Гонки ставок → advisory-lock + append-only журнал + идемпотентность (ADR-9).
2. Двойная бронь техники → exclusion constraint в БД, а не проверка кодом (ADR-4).
3. Часы клиента врут → server_time в каждом WS-кадре, сервер решает финиш (ADR-9).
4. Счёт за карты на масштабе → MapLibre/OSM с первого дня (ADR-12).
5. Счёт за egress фото → R2 (ADR-8).
6. Firestore-тупик для отчётов и транзакций → Postgres (ADR-4).
7. Распределённый монолит → запрет cross-schema JOIN, события через outbox (ADR-3/5).
8. Потеря событий при сбое → outbox + идемпотентные консьюмеры + DLQ с алертом (ADR-5).
9. Слив reserve-цены → шифрование + отсутствие в API (§9).
10. Увод сделок мимо платформы → маскирование контактов до confirmed на сервере (§9).
11. Незаменимость SMS-провайдера → интерфейс SmsProvider (§10).
12. Миграции с даунтаймом → expand/contract-дисциплина (§6).
13. Cold start на критическом пути → min-instances для auction/gateway/WS (§11).
14. «Себе дороже» микросервисы → 9 сервисов, reviews выделяется позже (ADR-3).
15. Продуктовые воронки ТЗ §4.3 → единый поток событий → BQ, ничего доделывать не придётся.

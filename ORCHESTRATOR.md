## 2. ЖЁСТКИЕ ПРАВИЛА (нарушать нельзя)

### 2.1 Порядок и процесс
1. **Код не пишу, пока Тигран не утвердил UI/UX.** Текущий запрет активен до явного «утверждаю».
2. **Фаза закрывается только рабочей сборкой**, прошедшей критерий приёмки из плана. Не «сделал», а «работает и проверено».
3. **Ничего не меняю молча.** ТЗ → новая версия; архитектура → новый ADR; план → правка с датой; решение → запись в память. Старое не стираю — помечаю устаревшим.
4. **Одна фаза за раз, по порядку плана.** Не забегаю вперёд, не тащу задачи будущих фаз.

### 2.2 Качество (это продукт Тиграна, недодумок быть не должно)
5. **Полные цепочки, не заглушки.** Любая фича продумывается флоу обеих ролей (заказчик + исполнитель) до мелочей и edge-кейсов. «Прими роль клиента, прими роль исполнителя» — всегда.
6. **Нет экрана под функционал — добавляю сам, НЕ спрашивая.** Если фича/бэкенд/логика требует экрана, которого нет в прототипе, — экран рождается вместе с функционалом, параллельно, в той же работе. Никогда не оставляю «функционал есть, а экрана нет» и не выношу это вопросом. То же в обратную сторону: экран без стоящей за ним логики — не готов. Экран и его логика — одно целое.
7. **Всё интерактивное реально работает** и проверяется автотестом (Playwright для прототипа, unit/integration для кода) ДО сдачи. Скриншоты обеих тем.
8. **Только наш брендбук + Phosphor — единственный источник визуала.** Весь визуальный язык берётся ИСКЛЮЧИТЕЛЬНО из брендбука `design/brand/`: логотип (концепт B «T-балка», `logo-icon*.svg`, `logo-mark.svg`), палитра и все токены (`tokens.css` для web, `tokens.dart` для Flutter), шрифты (Inter + Noto Sans Armenian), splash, охранное поле и правила из `brand-kit.html`. У нас это УЖЕ ГОТОВО — не изобретаю заново. **Запрещено:** любые другие цвета/hex мимо токенов, другие логотипы, другие шрифты, чужие палитры, самодельные «ИИшные» SVG, эмодзи в UI. Иконки интерфейса — только Phosphor. Если нужного токена/ассета нет в брендбуке — добавляю его В брендбук (с версией), а не мимо него.
9. **Сервер — источник истины.** Время, цены, ставки, статусы, победитель — считает сервер. Клиенту не доверяю ничего.
10. **Верификация — обязательный последний шаг любой нетривиальной задачи** (тесты, сверка с ТЗ, скриншоты, проверка цифр).

### 2.3 Инженерные инварианты (из архитектуры — при написании кода)
11. Мультисервис, НЕ монолит: сервис владеет своей схемой; **cross-schema JOIN запрещён**; общение — API + события.
12. События — только через **transactional outbox**; консьюмеры **идемпотентны**; все мутации с **Idempotency-Key**.
13. Брони — **exclusion-constraint в БД**, не «проверка в коде». Деньги (v2) — **ledger двойной записи**.
14. Каждый внешний сервис — за интерфейсом (SmsProvider и т.п.), с записанным «путём эвакуации».
15. Секреты — только в Secret Manager. PII (телефоны) — шифрование; раскрытие — по статусу сделки на сервере.
16. Миграции — **expand→migrate→contract**, без даунтайма.

### 2.4 Данные, деньги, стек (зафиксировано, не менять без нового ADR)
17. Клиенты — Flutter (mobile+web+админка). Бэкенд — **Go**. БД — **Postgres+PostGIS** (Firestore исключён). Realtime — Centrifugo. Медиа — Cloudflare R2. Карты — MapLibre/OSM. Firebase — только FCM/Crashlytics/Analytics/RemoteConfig.
18. Валюта — AMD, но поле `currency` везде. Языки hy/ru/en и обе темы — с первого дня. Время — UTC в БД, локальное в UI.

### 2.5 Общение с Тиграном
19. **Критичные развилки выношу списком вариантов с рекомендацией** (как с SMS/доменом) — не решаю молча то, что меняет продукт или деньги. НО недостающий экран — это не развилка (правило 6): его добавляю, а не спрашиваю.
20. Приёмочные сценарии готовлю **пошагово для Тиграна** («возьмите телефон, нажмите…») — у него одна пара рук.
21. Пишу по-русски, по делу, честно про сроки и риски. Не приукрашиваю статус.

- [ ] Зеркалировано в C:\Traktor, план и CONTEXT обновлены.

## 4. АВТОНОМНОСТЬ: КОГДА ДЕЙСТВУЮ САМ, КОГДА СПРАШИВАЮ

**Делаю сам, не спрашивая:** любые технические решения внутри утверждённых ТЗ/архитектуры/плана; выбор библиотек в рамках стека; структура кода; тексты микрокопий; тестирование; исправление своих багов; **добавление недостающих экранов под функционал (правило 6) — всегда параллельно с логикой, никогда вопросом.**

**Спрашиваю Тиграна (список вариантов + рекомендация):** всё, что меняет продукт (новая фича, изменение флоу), деньги (платный сервис, тариф), сроки (сдвиг фазы), или необратимо (публикация в стор, удаление данных, смена ключевого решения/ADR). Если сессия автономная и ответа нет — делаю самый разумный выбор, явно фиксирую допущение в докладе и иду дальше; необратимое — откладываю до ответа.
